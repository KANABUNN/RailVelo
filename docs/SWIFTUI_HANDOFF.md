# SwiftUI画面工程への引継ぎ

## 組み込みの入口

ローカルSwift Packageの `RailVeloCore` を計算用、`RailVeloSQLite` をデータ読取用、`RailVeloLocation` をCore Location変換用として追加する。`data/railway.sqlite` をアプリの読み取り専用リソースとして同梱する。起動時にNetworkを1回読み込み、乗車ごとにMapMatcherを作る。

MapMatcherは状態を持つため、同一インスタンスへの入力は1つの直列キューまたはactorにまとめる。描画更新はMainActorへ渡す。計算コアからCLLocationManagerやSwiftUIを呼び出さない。

## 画面へ渡す値

| 表示 | 元フィールド / 規約 |
| --- | --- |
| 速度 km/h | Core Locationの有効速度×3.6。速度無効時は「取得中」。マッチ結果には速度計用の確定速度を含めていない |
| 路線名 | routeIdからNetwork.routesを参照。未確定時は候補表示または「判定中」 |
| 方面 | directionLabel。候補のdirectionはエッジ向きなので直接表示しない |
| 直前駅・次に通過する駅 | previousStationId / nextStationIdを駅辞書で表示 |
| 次駅まで | distanceToNextM。N02代表線形の弧長としてm/km表示 |
| 駅間進捗 | progress 0〜1。nullなら進捗表示を保留 |
| 測位の状態 | matched / predicted / uncertain / lost / rejected |
| GPS精度・推定の不確実性 | uncertaintyM。confidenceは相対支持度で較正済み精度ではない |
| 到着・発車・通過 | events。通知や記録はイベントごとの推定時刻・駅ID・信頼度を保存 |

`matched` は実測、`predicted` は短時間の予測として画面に明示する。位置を失ったときに最後の値を現在値として表示し続けない。`uncertain` では候補点を薄く描画できるが、確定した方面・前後駅として表示しない。

駅の中心でのノイズによりnextStationIdが切り替わり得るため、停車中は到着イベントによる駅名表示を優先する。ただし駅イベントは測位の途切れで継続できない場合がある。「次の停車駅」「到着予定時刻」「列車種別」を残距離から生成しない。

## 画面工程で行う検証

1. macOSでSwiftテストと全共通データのPython/Swift比較を実行し、Simulator向けビルドを確認する。
2. 位置情報の用途説明、権限拒否・概算位置・無効速度・測位停止を実装する。バックグラウンド権限や常時記録は利用目的と電池消費を別途判断する。
3. 前面動作で門司港〜博多の実走ログを取得し、個人情報を含むログの保存・削除操作を用意する。
4. 分岐・並走・折尾の駅線形・長いホーム・低速・トンネル・信号待ちを実走で検証し、イベントの既定値と方向の安定性を調整する。
5. iPhoneで処理時間・メモリー・電池消費・更新頻度を計測する。今回のWindows処理時間をiOS性能の保証に使わない。

## 未解決事項

- 本作業ではSwiftコンパイラー/macOS/iPhone実機を利用できず、ビルドと両言語の実行一致は未確認。
- v0.2設計書本文のライブラリ原本は今回再取得していない。元SQLと前工程の設計対応記録に基づく継承。
- 線路ごとの上下線・転轍器の接続可否・ホーム停止位置はN02だけでは確定しない。
- 他路線への直通、別経路の駅距離、列車ごとの停車駅は追加データが必要。
- 信号待ちと駅停車の完全な識別、トンネル内の加減速、較正した確率・誤差半径は未実装。
- 暫定の在来線速度上限・推定閾値の設定化、現地ログによる調整、ループ経路、全国データの分割配信は次の拡張課題。
